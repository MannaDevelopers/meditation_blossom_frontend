# Issue #221: iOS WidgetKit - 디자인 값 렌더링 반영 — 구현 계획

**Goal:** `ios/MeditationBlossomWidget/MeditationBlossomWidget.swift`가 App Group에 저장된 `WidgetDesign`(#220의 브릿지가 저장) 값을 읽어 실제 홈 화면 위젯(`.systemMedium`/`.systemLarge`)에 반영하도록 한다 — 텍스트(정렬/색상/크기/두께)와 배경(단색 또는 갤러리 이미지, focalX/focalY 기준 cover-fit)을 지금까지 하드코딩돼 있던 상수 대신 동적으로 적용한다.

**배경**: `#220`(iOS 위젯 디자인 브릿지) PR 작업 중 사용자가 실기기에서 EditScreen 편집 → 저장을 해봤지만 홈 화면 위젯이 그대로였던 것을 발견 — 원인은 버그가 아니라 저장 계층(#220)과 렌더링 계층(#221)이 애초에 분리된 sub-issue였고 #221이 아직 미착수였기 때문. 이 세션에서 이어서 #221을 구현.

**Architecture 결정**: `MeditationBlossomWidgetExtension` 타깃은 앱 타깃(#220의 `WidgetUpdateModuleImpl`)과 별개 모듈이라 그쪽 `WidgetDesignPersistence.Design` Codable 타입을 공유할 수 없다 — `Sermon.swift`가 이미 같은 이유로 JS 타입을 이 타깃 안에서 따로 미러링하는 것과 동일한 패턴을 따라, `MeditationBlossomWidget.swift` 파일 안에 자체 `WidgetDesign`/`WidgetTextDesign`/`WidgetBackgroundDesign`/`WidgetImageTransform` Codable 타입을 새로 정의했다. `src/components/WidgetPreview.tsx`의 `IOSWidgetFrame`(Android처럼 배너/카드 이중 레이어가 아니라 단일 레이어 구조, 제목/장절도 본문과 동일한 `design.text.size`/`color`를 쓰되 두께만 고정)을 그대로 따라 Swift로 이식했다 — RN 미리보기가 두 플랫폼 디자인 규칙의 단일 소스이므로 실제 위젯도 그 결과와 일치해야 한다.

**Tech Stack:** Swift, SwiftUI, ImageIO 불필요(단순 `UIImage(contentsOfFile:)` + `GeometryReader` cover-fit 배치로 충분 — #220의 다운샘플링은 저장 시점에 이미 끝나 있음).

**테스트 정책**: 이슈 본문이 "실기기/시뮬레이터 수동 확인"만 요구(#220과 달리 단위 테스트 요구 없음) — `WidgetExtension` 타깃은 별도 XCTest 타깃이 없고 새로 만들려면 pbxproj에 타깃을 통째로 추가해야 해서 이슈 스코프를 벗어난다. 대신 시뮬레이터에서 실제 검증:
1. 실기기 빌드가 디스크 부족(`No space left on device`)으로 실패 → `~/Library/Developer/Xcode/DerivedData` 정리로 해결(이슈 코드와 무관, 별도 트러블슈팅).
2. RN `EditScreen`에서 텍스트 정렬(우측)/색상(파랑)/크기(28pt)/두께(극굵게)를 실제로 편집·저장 → 홈 화면에 위젯을 새로 추가 → 변경사항이 그대로 반영되는 것을 스크린샷으로 확인(브릿지+렌더링 전체 파이프라인 end-to-end 검증).
3. 갤러리 배경 경로는 `xcrun simctl spawn defaults write`로 App Group `UserDefaults`에 `background.type: "gallery"` 값(테스트용 이미지 경로 포함)을 직접 주입한 뒤, 앱을 재실행해 `onSermonUpdated`가 부수적으로 트리거하는 `reloadWidgets()`로 타임라인을 새로고침 → 위젯 배경이 실제로 그 이미지를 cover-fit으로 그리는 것을 스크린샷으로 확인(임의 이미지가 정확히 렌더링되어, `GalleryBackgroundView`의 `baseScale`/`focalX`/`focalY` 계산이 정상 동작함을 입증).

**빌드 검증**: macOS + Xcode 26.3 — `xcodebuild build`로 실제 컴파일 확인(성공).

**커밋 정책:** `feature/issue-221` 브랜치(`feature/issue-220` 기반 — #221이 #220의 브릿지 저장 로직에 의존하므로 스택). 커밋 메시지 `[ISSUE-221] type: 설명`. PR은 `feature/issue-220`을 base로 생성(#220 머지 후 자동으로 diff가 #221분만 남음).

### Task 1: `WidgetDesign` 미러 타입 + 순수 변환 헬퍼 추가

**File:** `ios/MeditationBlossomWidget/MeditationBlossomWidget.swift`

- `WidgetImageTransform`/`WidgetTextDesign`/`WidgetBackgroundDesign`/`WidgetDesign` Codable 구조체(src/types/WidgetDesign.ts 미러) + `defaultWidgetDesign` 상수(편집 전 하드코딩 스타일과 동일: left/#000000/16/regular, color/gradient-default) 추가.
- `hexColor(_:) -> Color`: 잘못된 hex여도 크래시 없이 검정 폴백.
- `contentFontWeight(_:) -> Font.Weight`: regular→.regular, bold→.bold, extrabold→.heavy(SwiftUI가 Android Glance보다 넓은 weight를 지원하므로 근사 없이 매핑). 본문에만 적용(제목/장절은 고정 두께, RN `IOSWidgetFrame`과 동일 규칙).
- `textAlignment(_:) -> TextAlignment` / `frameAlignment(_:) -> Alignment`: left/center/right 매핑.
- `clampFocal(_:_:) -> Double`: `src/utils/imageCropMath.ts`의 `clampFocal`과 동일 로직.
- `dividerColor(onPhoto:) -> Color`: 갤러리 배경이면 흰색 40% 불투명도, 아니면 기존 다크 12%(RN `IOSWidgetFrame`의 `dividerColor` 분기와 동일).
- `PhotoTextShadow` ViewModifier + `widgetTextShadow(onPhoto:)`: 사진 위 텍스트 가독성을 위한 그림자(RN `textOnPhotoShadow`와 동일 값).

## Self-Review 결과

- **이슈 커버리지**: "폰트 크기/색상 등 하드코딩 값을 WidgetDesign으로 대체", "텍스트: 정렬/색상/크기/두께", "배경: 단색 또는 갤러리 이미지(cover-fit, focalX/focalY)", ".systemMedium/.systemLarge 두 크기 모두 확인" — 이슈 본문의 모든 항목을 다뤘다.
- **스코프 경계**: `Sermon.swift`는 디자인 필드를 미러링할 필요가 없어(design은 완전히 별개 App Group 키) 변경하지 않았다 — 이슈 본문의 "필요 시"라는 단서대로 불필요했다. QT 위젯(`DailyMannaWidget.swift`)은 이슈의 "대상 파일" 목록에 없어 그대로 뒀다.
- **기존 컨벤션 재사용**: `src/components/WidgetPreview.tsx`의 `IOSWidgetFrame`(제목/장절 두께 고정, 본문만 weight 반영, accent 색상 제거, textOnPhotoShadow, dividerColor 분기)을 그대로 이식 — 두 플랫폼(RN 미리보기·실제 iOS 위젯)이 시각적으로 어긋나지 않도록 새 규칙을 만들지 않고 기존 RN 소스를 따랐다. `WidgetDesign` 미러링은 `Sermon.swift`의 기존 패턴을 그대로 따름.
- **리스크**: (1) 이 Mac의 디스크 여유공간이 정리 직후에도 8~12GB 수준으로 빠듯해 반복 빌드 시 다시 부족해질 수 있음(코드 문제 아님, 별도 정리 권장). (2) 두 곳(#220 브릿지, #221 렌더링) 모두 App Group `UserDefaults`의 `"widget_design"` 문자열 키를 각자 하드코딩하고 있어 — 오타 등으로 어긋나면 조용히 기본값으로 폴백한다(현재 두 값이 일치하는지는 수동 확인함, 향후 상수를 공유 파일로 뽑으면 더 안전하지만 두 타깃이 서로 다른 모듈이라 현재 구조로는 오버엔지니어링).
