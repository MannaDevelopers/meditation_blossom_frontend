# Issue #263: 시스템 다크모드 지원 - 앱 전체 라이트/다크 테마 적용 — 구현 계획

**Goal:** 시스템(iOS/Android) 설정이 다크모드일 때 앱 UI(화면 배경/텍스트/카드/구분선/상태바/네비게이션)가 자동으로 다크 테마로 전환되게 한다.

**현재 상태 조사 요약**:
- `useColorScheme`/`Appearance` 사용처 없음 — 앱이 시스템 테마를 아예 조회하지 않음.
- 중앙화된 색상 토큰 없음. 6개 화면(`HomeScreen`, `SettingsScreen`, `DailyMannaScreen`, `TempSermonScreen`, `ImageCropScreen`, `EditScreen`) + 2개 컴포넌트(`ForceUpdateModal`, `WidgetPreview`)에 hex 리터럴이 하드코딩되어 있음(스크린 6개 파일에 약 97개).
- `@react-navigation/native`는 설치돼 있으나 `NavigationContainer`에 `theme` prop 미전달.
- Android `AppTheme`은 `Theme.AppCompat.DayNight.NoActionBar`를 상속하지만 `styles.xml`에서 상태바를 흰색/라이트로 고정, `values-night/` 리소스 없음.

**핵심 스코프 판단 — "앱 크롬" vs "위젯 디자인 콘텐츠" 구분** (중요):
`EditScreen.tsx`와 `WidgetPreview.tsx`는 사용자가 홈 화면 위젯에 표시할 텍스트/배경 색상을 직접 고르는 화면이다. 이 위젯 디자인 색상(`WidgetDesign.text.color`, `WIDGET_TEXT_COLOR_PRESETS`, 위젯 미리보기 렌더링 등)은 **사용자가 명시적으로 선택한 값**이며 시스템 테마와 무관하게 항상 그대로 유지되어야 한다(안 그러면 사용자가 고른 위젯 배경색이 폰 다크모드 설정에 따라 제멋대로 바뀌는 버그가 된다). 다크모드 적용 대상은 오직 **편집 화면 자체의 UI 크롬**(탭 바, 버튼, 모달 배경, 구분선, 화면 배경 등 앱이 그리는 UI)이다. 이 구분은 [#261](https://github.com/MannaDevelopers/meditation_blossom_frontend/issues/261)에서 EditScreen의 "UI 크롬 vs 위젯 디자인 콘텐츠"를 이미 한 번 분리한 선례가 있다.

**설계**:
- `src/theme/colors.ts` — `ThemeColors` 타입 + `lightColors`/`darkColors` 토큰 + `getThemeColors(scheme: ColorSchemeName): ThemeColors` 순수 함수.
- `src/hooks/useAppTheme.ts` — `useColorScheme()`을 감싸 `{ colors, isDark }`를 반환하는 훅.
- 각 화면: 모듈 최상단 `const styles = StyleSheet.create({...})` → `const createStyles = (c: ThemeColors) => StyleSheet.create({...})` 함수로 전환하고, 컴포넌트 내부에서 `const { colors } = useAppTheme(); const styles = useMemo(() => createStyles(colors), [colors]);`로 교체. (React Native `StyleSheet.create`는 값 자체는 정적일 필요가 없고 매 렌더 새 객체를 반환해도 되므로 이 패턴이 표준적이다.)
- `EditScreen.tsx`: `styled-components`이므로 `ThemeProvider`를 도입해 크롬 관련 styled 컴포넌트만 `props.theme.colors`를 사용하게 하고, 위젯 디자인 값을 렌더링하는 부분(프리셋 스와치, 미리보기)은 기존 하드코딩 값을 그대로 둔다.
- `App.tsx`: `StatusBar`/최상위 `SafeAreaView` 배경, `NavigationContainer`의 `theme` prop(커스텀 `AppLightTheme`/`AppDarkTheme`, `DefaultTheme`/`DarkTheme` 확장)을 연결.
- Android: `values-night/styles.xml` 추가해 다크모드일 때 상태바 색상/아이콘 톤을 어둡게 분기.

**Non-goals**: iOS/Android 홈 화면 위젯(WidgetKit/Glance) 자체의 다크모드 대응(이슈 본문에 명시된 범위 제외 — 별도 후속 이슈). 위젯 디자인 콘텐츠 색상(사용자가 고른 프리셋)은 대상 아님.

**테스트 정책**: `getThemeColors` 같은 순수 함수는 `__tests__/theme/colors.test.ts`에 단위 테스트 추가. 화면 렌더링 자체의 다크모드 전환 확인은 시뮬레이터/에뮬레이터가 필요하다 — 이 세션은 (Windows, 실기기/에뮬레이터 미연결) 코드 레벨 검증(`yarn test`, `yarn lint`, `yarn tsc`)까지만 수행하고, 실제 다크모드 육안 확인은 PR 설명에 사용자 몫으로 명시한다.

**커밋 정책**: `feature/issue-263` 브랜치. 커밋 메시지 `[ISSUE-263] type: 설명`.

## Self-Review 체크리스트 (구현 후 확인)

- EditScreen/WidgetPreview에서 위젯 디자인 콘텐츠 색상과 UI 크롬 색상을 실수로 섞어 바꾸지 않았는지 재확인 — 사용자가 고른 위젯 배경/텍스트 색이 다크모드 전환 시 변하면 안 됨.
- `accent`(`#00A8DE`) 등 브랜드 컬러를 라이트/다크 동일하게 유지하기로 한 결정이 실제 다크 배경에서도 대비(가독성)가 충분한지 코드 리뷰 시점에서 재확인.
- 각 화면에서 `StyleSheet.create` 호출을 컴포넌트 내부로 옮기면서 불필요한 리렌더/성능 저하가 없는지(`useMemo` 의존성 배열에 `colors` 객체 참조가 안정적인지 — `useAppTheme`이 매 렌더 새 객체를 반환하지 않는지) 확인.
- Android `values-night/styles.xml`이 `values/styles.xml`과 다른 속성을 실수로 빠뜨리지 않았는지(상속 구조상 명시하지 않은 속성은 기존 값 유지되므로 필요한 속성만 오버라이드하면 됨).
